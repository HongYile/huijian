# 端到端加密：客户端实现规格

> 给 Mac、iPhone、安卓（以后 Windows）客户端的开发者。三端按这份规格实现，行为和文案保持一致。
> 设计与安全理由见 [e2ee.md](e2ee.md)，服务端接口见 [api.md](api.md)「端到端加密」「新登录协议」。

## 0. 共用核心

所有密码学计算都调用共用核心（`core/`，Rust），不在各端自己实现：

| 端 | 封装 | 构建 |
|---|---|---|
| Mac / iPhone | `Sources/Core.swift`（两端同一份） | `build.sh` 里自动执行 `../core/build.sh mac / ios / ios-sim`，静态链接 |
| 安卓 | `Core.kt` | Gradle 任务 `buildCore` 自动执行 `core/build.sh android`，生成 `jniLibs/arm64-v8a/libhuijian_core.so` |

操作一览见 `core/src/api.rs` 开头的注释。约定：钥匙、随机数、凭证是 base64url（无填充）字符串，盐是十六进制。
Argon2id 一次约 0.1–0.4 秒、占 64 MiB 内存：**不要在主线程调用**，也不要并发调用多次。

## 1. 本地存储

| 内容 | 存放位置 | 说明 |
|---|---|---|
| 账号私钥（可能多把，按 kid 区分） | Mac / iPhone：钥匙串（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`，不同步 iCloud）；安卓：和登录 token 相同的 Keystore 加密存储 | 按「服务器 + 账号 id」区分；退出登录、设备被移除时删除 |
| 等待批准时生成的设备钥匙对 | 同上 | 拿到转交的私钥后删除 |
| 开启加密进行中的新钥匙对和恢复码 | 同上 | 见 §4.1：从生成到用户点「完成」之间都存着，App 被系统终止也不丢；点「完成」、确认开启失败、退出登录时删除 |
| 「这个服务器上的这个账号已升级」标记 | 普通偏好设置（不是秘密） | 按「服务器地址 + 用户名（小写）」记，退出登录也**不删** |
| 钉住的账号公钥 | 普通偏好设置（不是秘密） | 按「服务器地址 + 账号 id」记；本机第一次保存账号私钥时写入 `Core.publicKey(sk)`，之后不再改；退出登录也**不删**。用途见 §4.5、§7 第 1 项 |
| 解密后的消息内容 | 和现在的本地消息缓存一样 | 同时保留信封原文 `e2e`，解锁后可以重新解密 |
| 解密后的附件 | 和现在的附件缓存一样，用真实文件名 | 密文下载完、解密成功后删除密文 |

钥匙串 / Keystore 读写失败时，不要崩溃：当作「未解锁」处理，并在加密页显示原因。

「服务器地址」要先规范化再当作键：scheme 和 host 小写，去掉默认端口（http 的 80、https 的 443）和末尾的 `/`。否则换一种写法（`https://x:443`）就能绕过「已升级」标记和钉住的公钥。

**本地字段不能来自服务器**：解密状态（例如 `e2e_status`）、附件钥匙 `key`、「仅本机保留」等只在本机产生的字段，解码服务端响应时一律丢弃（清空），只能由本机解密或本机逻辑写入。否则被攻破的服务器可以在 JSON 里带上「已解密」和自己写的文字，冒充一条 🔒 消息。

macOS 的钥匙串说明：没有开发者签名时无法使用数据保护钥匙串，钥匙项存在 login 钥匙串里，`ThisDeviceOnly` 不起作用（不会同步 iCloud，但迁移助理和整机备份会带到别的 Mac）。这一点在 e2ee.md 的局限里注明。

## 2. 登录、注册、自动升级

服务端没有 `e2e` 功能（`GET /v1/prelogin` 返回纯文本 404）时，按原来的方式登录。但如果这个账号已经标记为「已升级」，就拒绝登录，并显示 **T1**。

「服务端没有 e2e」只能由 prelogin 的纯文本 404 判断。功能清单还没取到、网络出错、prelogin 返回 5xx 时**不能**当作没有 e2e，按出错处理。

### 2.1 账号密码登录

1. `GET /v1/prelogin?username=`。
2. 返回 `kdf: argon2id`：
   - 先核对参数。`time`=3、`memory_kib`=65536、`lanes`=1，`salt` 至少 16 字节（32 位十六进制），否则拒绝并显示 **T2**。
   - 用 `Core.passwordKeys(密码, salt)` 算出 `auth_key` 和 `unlock_key`，发送 `POST /v1/login {username, auth_key, name, platform, fingerprint}`。
3. 返回 `kdf: pbkdf2-sha256`：
   - 如果本地标记该账号「已升级」，拒绝并显示 **T1**。唯一的例外见 §4.4 第 4 步（重新设置密码页）。
   - 否则用 `Core.pbkdf2(密码, salt, iterations)` 算出 `password_key`（轮数不够时核心库报 weak_params，显示 **T2**），发送 `POST /v1/login {username, password_key, …}`。
4. **从不**发送 `password` 原文。只有一个例外：prelogin 返回纯文本 404，且这个账号没有「已升级」标记。这条同样适用于注册（§2.2）、改用户名和改密码（§7 第 5 项）。
   - 设置初始密码（账号还没有密码，`has_password` 为假）没有新接口，只能发原文：本机标记了「已升级」时拒绝（显示 T1），否则发原文，成功后立即按 §2.1 第 7 步升级。
   - 开启加密、更换恢复码、重新设置密码这三个操作调用的是 `/v1/e2e/*` 和新接口，服务端一定有 prelogin：prelogin 返回 404 时直接报错，**不**发原文。
5. 登录响应 `426`：显示服务端给的说明（「请把回笺更新到最新版」类）。
6. 用 argon2 登录成功后：
   - 把账号标记为「已升级」。
   - 如果响应里 `e2e.enabled`，并且有 `e2e.password_wrap`，执行 `Core.unwrap("hjp1", unlock_key, password_wrap)` 得到私钥，再按 **§4.5** 核对后保存。
   - unwrap 失败（例如管理员重设过密码）时进入「已锁定」状态，不阻止登录。
7. 用 PBKDF2 登录成功后，**立即自动升级**：
   1. 先 `GET /v1/e2e`。如果 `enabled` 为真（说明管理员重设过密码，旧的密码副本已失效），先不升级，进入「已锁定」状态，等用户解锁后在 **§4.4** 里完成。
   2. 否则 `salt = Core.newSalt()`，`(auth, unlock) = Core.passwordKeys(密码, salt)`，发送 `PUT /v1/account/auth {current_password_key, auth_salt: salt, auth_key: auth}`。
   3. 成功后标记「已升级」。
   4. 失败不影响登录，下次登录再试。

`unlock_key` 只在内存里用完即弃，不落盘。

登录时解开的私钥要等拿到账号 id 才能保存。`/v1/me` 等后续请求失败时，把私钥留在内存里重试，不要静默丢弃。

配对码登录的设备：`GET /v1/e2e` 显示账号已用新方式登录（`auth_key` 为真）时，按 `/v1/me` 的用户名补记「已升级」标记。

### 2.2 注册

1. 先用 `Core.passwordProblem(密码, 用户名)` 检查密码强度，不合格时把原因显示在密码框下面。
2. 新协议注册：`salt = Core.newSalt()`，`(auth, _) = Core.passwordKeys(密码, salt)`，发送 `POST /v1/register {username, auth_key, auth_salt: salt, name, platform, fingerprint}`。
3. 成功后标记「已升级」。

### 2.3 配对码登录

和原来一样。登录后，如果账号已开启加密，这台设备处于「已锁定」状态（它从没输过密码）。

### 2.4 「当前密码」凭证（改密码、开启加密、换恢复码等需要核对当前密码的地方）

`GET /v1/prelogin?username=<自己的用户名>`，按 2.1 的规则算出 `current_auth_key`（argon2）或 `current_password_key`（pbkdf2），同样核对参数、同样遵守「已升级」标记。服务端返回 `403` 时显示 **T3**。

账号有密码（`has_password` 为真）时，改用户名、改密码一律走这里，不管功能清单取没取到、服务端是否隐藏了 e2e，也不管本机是不是管理员设备。只有 prelogin 返回纯文本 404 且没有「已升级」标记时，才能按旧接口发原文。

## 3. 加密状态

加密页和消息列表都根据 `GET /v1/e2e` 和本地私钥算出状态：

| 状态 | 条件 | 表现 |
|---|---|---|
| 未开启 | `enabled` 为假 | 加密页显示「开启端到端加密」入口 |
| 已解锁 | `enabled` 为真，本机有私钥，且对应的公钥是 `keys` 里某把 `active` 的钥匙 | 正常解密 |
| 已锁定 | `enabled` 为真，本机没有可用的私钥 | 消息列表顶部显示横幅 **T10**，点开进入解锁页（§4） |

刷新时机：
- 登录后；
- App 回到前台；
- 长轮询收到 `kind: "e2e"` 的变更时（同时可能有新的批准请求，见 §5）；
- 加密页打开期间每 3 秒一次（只在等待批准、等待核对时）。

入口位置：
- Mac：设置 →「加密」标签页；
- iPhone：设置 → 账户 →「端到端加密」；
- 安卓：设置 →「端到端加密」。

## 4. 开启加密与解锁

### 4.1 开启加密（`POST /v1/e2e/setup`）

页面文案见 **T20**。

1. 表单：
   - 当前密码；
   - 「同时换一个新密码（推荐）」复选框，默认勾选；
   - 勾选时显示新密码和确认新密码。
2. 检查：
   - 实际使用的密码（勾选时为新密码，不勾选时为当前密码）必须通过 `Core.passwordProblem`。
   - 当前密码不合格又没勾选换密码时，提示「当前密码不够安全，请换一个新密码」，并自动勾选。
3. 计算（在后台线程）：
   - `kp = Core.keypair()`
   - `salt = Core.newSalt()`；`(auth, unlock) = Core.passwordKeys(实际密码, salt)`
   - `password_wrap = Core.wrap("hjp1", unlock, kp.sk)`
   - `(code, rkey) = Core.recoveryNew()`；`recovery_wrap = Core.wrap("hjr1", rkey, kp.sk)`
   - 「当前密码」凭证按 §2.4 计算
4. `POST /v1/e2e/setup {pub: kp.pub, auth_salt: salt, auth_key: auth, password_wrap, recovery_wrap, current_…}`。返回 `409` 表示别的设备刚开启过，重新读取状态。
   - 网络出错或 5xx 时，**不要**马上丢掉 `kp` 和恢复码：先重新 `GET /v1/e2e`。`enabled` 为真、而且 active 公钥就是 `kp.pub`，说明其实已经开启成功，按第 5 步继续；`enabled` 为假，可以让用户重试；公钥不是 `kp.pub`，才丢弃。取不到状态时把 `kp` 和恢复码留在内存里，提示稍后重试（重试也先做这一步检查）。
5. 成功后：
   - 保存 `kp.sk`，标记「已升级」；
   - 进入「保存恢复码」页（**T21**）：大字等宽显示 `code`，提供复制按钮；
   - 必须勾选「我已把恢复码保存好」才能点「完成」；
   - 恢复码只显示这一次，不保存在本机。
   - 恢复码放在 App 的状态里（不是某个页面或窗口的临时状态），直到用户点「完成」才清除；关掉页面后再打开，还能看到这一页。
   - 新钥匙对和恢复码从第 3 步生成起就存进钥匙串 / Keystore（和私钥同等保护；恢复码只能解开同一把私钥，存在同一处不增加风险），点「完成」后删除。这样用户切到密码管理器保存恢复码时 App 被系统终止，或者第 4 步结果不确定时 App 被关掉，重新打开后都还能回到「保存恢复码」页。
   - 有进行中的开启（存着新钥匙对）时，**每次**刷新状态都检查：`enabled` 为真且 active 公钥就是这把 → 按第 5 步完成（保存私钥、钉住公钥、显示恢复码页）；`enabled` 为真但公钥不同 → 删除；`enabled` 为假 → 保留，提示用户重试。不要等用户再点「开启」才检查，因为开启成功后「开启」按钮就不显示了。
   - 「保存恢复码」页显示期间，App 进入后台时遮住恢复码（防止进入多任务截图）；安卓用 `FLAG_SECURE`。
6. 完成后提示 **T22**，告诉用户去 Pushkey 页复制加密发送密钥。

### 4.2 用密码解锁（配对码登录的设备，`POST /v1/e2e/unlock`）

输入密码 → 按 §2.4 算出 auth_key 和 unlock_key → `POST /v1/e2e/unlock {auth_key}` → 用返回的 `password_wrap` 执行 `Core.unwrap("hjp1", unlock, …)` → 按 §4.5 核对后保存。

失败情况：
- `403`：显示 **T3**。
- `409`（密码副本已失效）：显示服务端说明，并引导用户使用另外两种方式。
- prelogin 返回 pbkdf2、本机又标记了「已升级」：同样拒绝计算，但这里显示 **T44**（不是 T1）。最常见的原因是管理员重设过密码。

### 4.3 请另一台设备批准（新设备一侧）

1. 定下账号公钥 `acc`：
   - 本机有钉住的公钥（§1）时用它；`GET /v1/e2e` 的 active 钥匙不是它时，显示 **T43** 并停止。
   - 没有时，用 `GET /v1/e2e` 的 `keys` 里**唯一**一把 active 钥匙的 `pub`（不是正好一把就显示 **T43** 并停止）。
2. `dev = Core.keypair()`，保存 dev 钥匙对；`nb = Core.random32()`；`commit = Core.sasCommit(dev.pub, account: acc, nonce: nb)`。
3. `PUT /v1/e2e/device {pub: dev.pub, request: true, commit}`。`acc` 和 `nb` 只存在内存里，App 重启后从第 1 步重来。
4. 显示等待页 **T30**，每 3 秒（以及收到 e2e 变更时）`GET /v1/e2e`，看 `device` 字段：
   - `challenge` 非空，且还没揭晓：先算出核对码 `Core.sasCode(dev.pub, account: acc, na: challenge, nb: nb)`（算失败就回到第 1 步），再发送 `POST /v1/e2e/reveal {nonce: nb}`，然后显示核对码（**T31**，按 3+3 位显示，例如 `482 913`）。
   - 已揭晓后 `challenge` 变了：说明对方重新开始，回到第 1 步（生成新的 nb，重新 PUT）。
   - `grant` 非空：
     - **只在本次请求已经揭晓、核对码已经显示之后**才处理；在这之前看到的 grant 一律忽略（hjg1 谁都能加密给 dev.pub，服务器可以伪造）。
     - 执行 `Core.grantOpen(dev.sk, grant)` 得到私钥，`Core.publicKey(sk)` 必须等于 `acc`，否则丢弃并显示 **T43**；再按 §4.5 核对后保存，删除 dev 钥匙对，显示「已解锁」。
   - `requested` 变成假且没有 grant：说明被拒绝了，显示 **T32**。只看本次 PUT 之后发出的 `GET` 结果，丢弃更早发出、晚到的响应（用一个递增的请求序号）。
5. 用户可以点「取消」：发送 `PUT /v1/e2e/device {pub: dev.pub, request: false}`。

为什么要把 `acc` 放进承诺：批准设备用**自己私钥算出的**账号公钥核对承诺。服务器如果给新设备看了假的账号公钥，承诺对不上，批准设备自动拒绝（T52）；新设备又只接受和 `acc` 配对的私钥，所以服务器没法让新设备收下它自己的私钥。

### 4.4 用恢复码解锁

1. 输入恢复码（**T40**），执行 `Core.recoveryKey(输入)`，格式不对时显示核心库给的说明。
2. 用 `GET /v1/e2e` 里的 `recovery_wrap` 执行 `Core.unwrap("hjr1", key, …)`。失败时显示 **T41**。
3. 按 §4.5 核对后保存。
4. 解锁后（包括 §4.3 的批准）如果 `auth_key` 为假，或者 `has_password_wrap` 为假：
   - 说明管理员重设过密码，账号回到了旧登录方式，或者密码副本已失效；
   - 引导用户进入「重新设置密码」页（**T42**）：输入当前密码（管理员重设后的密码）、新密码、确认新密码；
   - 发送 `PUT /v1/account/auth {current_…, auth_salt, auth_key, password_wrap}`，`password_wrap` 用新密码的 unlock 锁住本机私钥。
   - **只有这一页**计算「当前密码」凭证时允许走 pbkdf2，即使本机标记了「已升级」：这时的当前密码是管理员用原文设置的，服务器本来就知道，算出 PBKDF2 不会泄露新信息。其他地方（登录、用密码解锁、改密码等）仍按 §2.1 拒绝。
   - 已知的残余风险：这一页是否出现由服务器的回答决定。被攻破的服务器可以谎称「管理员重设过」，如果用户在这一页填了自己真正的密码，服务器能拿到它的 PBKDF2（60 万轮，比 Argon2 好猜）。所以 T42 明确要求填管理员给的临时密码。
   - 账号被管理员重设后，标记过「已升级」的设备用密码登录会被 T1 拦住：这时用配对码登录（另一台已登录的设备生成），再按本节解锁并重新设置密码。

### 4.5 保存私钥前的核对（必须）

用 `Core.publicKey(sk)` 算出公钥，核对：
1. 它是 `GET /v1/e2e`（或登录响应）的 `keys` 里一把 `active` 的钥匙；
2. 本机有钉住的账号公钥（§1）时，必须和它相同。

对不上就丢弃，并显示 **T43**。这一步防止被攻破的服务器塞给你一把它自己的钥匙。核对通过后保存私钥；还没有钉住的公钥时，把这把公钥钉住。

本机已经存着私钥、却没有钉住的公钥时（例如 iPhone 卸载重装后钥匙串里还留着私钥，偏好设置却清空了），刷新状态时按上面第 1 条核对这把私钥，通过就用它算出的公钥补钉。

各种拿到私钥的方式为什么可信：开启加密是本机生成的；密码副本和恢复码副本用服务器不知道的钥匙锁住（AES-GCM，服务器改不了）；批准转交靠 §4.3 的核对码绑定账号公钥。

## 5. 批准其他设备（已解锁设备一侧）

- `GET /v1/e2e` 的 `requests` 非空时：
  - 加密页显示「等待批准的设备」列表，每项显示设备名、平台、请求时间；
  - 系统通知 **T50**，同一个请求只通知一次。
- 点「批准」：
  1. `na = Core.random32()`（只用自己生成的随机数），发送 `POST /v1/e2e/challenge {device_id, nonce: na}`。返回 `409` 说明请求已被别的设备接手，显示 **T51**。
  2. 等待对方揭晓：每 3 秒（以及收到 e2e 变更时）刷新，直到这项请求出现 `reveal`。等待期间显示「拒绝」和「取消」按钮：「拒绝」发送 deny；「取消」只停止本机的等待。
  3. 核对 `Core.sasCommit(request.pub, account: 本机账号公钥, nonce: reveal) == request.commit`，其中「本机账号公钥」是 `Core.publicKey(本机账号私钥)`，**不用**服务器给的 keys。不一致时：
     - 立即发送 `POST /v1/e2e/deny {device_id}`；
     - 显示 **T52**。
  4. 显示核对码 `Core.sasCode(request.pub, account: 本机账号公钥, na: na, nb: reveal)`（**T53**），两个按钮：「一致，批准」「不一致，拒绝」。
  5. 点「一致，批准」：
     - `grant = Core.grantSeal(sk: 账号私钥, to: request.pub)`；
     - 发送 `POST /v1/e2e/grant {device_id, pub: request.pub, grant, kid}`（`kid` 是本机账号私钥的 kid，服务端 0.8.0 起校验，见 §11.5）；
     - 返回 `409` 时显示服务端说明（对方取消了或换了公钥）。
  6. 点「不一致，拒绝」：发送 `POST /v1/e2e/deny {device_id}`。
- 点「拒绝」（不核对，直接拒绝）：发送 `POST /v1/e2e/deny {device_id}`。

## 6. 收消息

### 6.1 解密

消息带 `e2e` 字段（信封 `hje1.…`）时：

1. 已解锁：调用 `Core.openMessage(keys: 本账号全部私钥, envelope)`，得到 `{v, text, desp, type, atts}`。
   - 显示用载荷里的 `text`、`desp`、`type`（`markdown` / `text` / `image`），忽略服务端给的占位文字、`doc` 和 `preview`。
   - 附件：载荷 `atts[i]` 对应服务端 `attachments[i]`（按顺序）。两边数量不一致时，整条消息按 `format`（**T62**）处理，不要截断或把多出的服务端附件当明文下载。显示用载荷里的 `name`、`mime`、`size`，下载用服务端的 `id`。附件钥匙 `key` 和消息一起保存，解密附件时要用。
   - Markdown：`type` 不是 `text` 也不是 `image`、且正文非空时（与服务端规则一致），调用 `Core.mdBuild(text, desp, atts: [{id: 服务端附件 id, name, mime, size}])`，得到 `doc` 和 `preview`，用现有的 doc 渲染代码显示，和服务端解析的明文消息一模一样。
2. 已锁定，或解密失败：
   - 标题显示 **T60**，正文为空；保留 `e2e` 原文。
   - 解锁后把所有还没解开的消息重新解密一遍。App 启动时、以及每次刷新状态后发现「已解锁」但还有没解开的消息时，也重新解密一遍（防止解锁和后台同步同时进行时漏掉，或钥匙串 / Keystore 偶发读取失败）。
   - `wrong_key`：可能是换过钥匙、本机没有那把旧钥匙，显示 **T61**。
   - `format`：显示 **T62**。
3. 解密在后台线程做（单条约 0.1 ms，批量同步时也要避免阻塞界面）。

### 6.2 通知

- 本机弹出的通知（Mac、安卓，以及 iPhone 在前台时）用解密后的标题和预览。
- 未解锁时，通知标题显示 **T60**。
- 优先级、频道、线程不加密，按原规则提醒。

### 6.3 标记

| 情况 | 列表 | 详情页 |
|---|---|---|
| 加密消息 | 标题前一个小锁图标（SF Symbol `lock.fill` / Material `Lock`），弱化颜色 | 元信息行显示「🔒 端到端加密」 |
| 账号已开启加密，但这条是明文 | 一个「未加密」灰色小徽章 | 元信息行显示 **T63** |
| 账号未开启加密 | 不显示任何标记 | 不显示任何标记 |

### 6.4 附件

1. 下载密文：`GET /v1/att/{id}`。`X-Huijian-Sha256` 是**密文**的哈希，照常校验。
2. 校验通过后，调用 `Core.decryptFile(key, 密文, 目标文件)`：
   - 目标文件用载荷里的真实文件名；
   - 成功后删除密文；
   - 失败时删除临时文件，附件卡片显示「解密失败」。
3. 自动下载的大小上限按载荷里的 `size` 判断。密文比明文略大，大约多 0.03%。

## 7. 设置项（已开启加密；除第 1 项外都要求本机已解锁）

1. **加密发送密钥**：Pushkey 页每把 key 下面多一行「加密发送密钥」，内容是 `<pushkey>.e2e.<公钥>`（公钥 43 个字符）。
   - 公钥**只用本机钉住的账号公钥**（§1，等于本机私钥算出的公钥），不用服务器 `keys` 里给的。否则被攻破的服务器改一下 keys，用户复制到脚本里的就是攻击者的密钥，之后的消息全部泄露。
   - 本机锁定、但已经钉住过公钥时照常显示。从没解锁过（没有钉住的公钥）时，这一行显示 **T73**，不显示密钥。
   - 服务器 `keys` 里的 active 钥匙和钉住的不同时，不显示密钥，显示 **T43**。
   - 提供复制按钮，旁边的说明见 **T70**。
   - 账号未开启加密时不显示这一行。
2. ~~只接受加密消息~~：**0.9.0 起取消**（2026-11-20 用户确认：所有消息都加密，没有「接受 / 不接受明文」的选项）。普通 pushkey 是「简单用法」：服务器收到后立即加密再发到设备（§11.5），客户端不再提供这个开关，也不调用 `PATCH /v1/e2e {e2e_only}`。
3. **更换恢复码**：先输入当前密码，然后：
   - `(code, rkey) = Core.recoveryNew()`，`recovery_wrap = Core.wrap("hjr1", rkey, sk)`；
   - 发送 `PUT /v1/e2e/recovery {recovery_wrap, kid, current_…}`（`kid` 见 §11.5，409 时显示 **T46**）；
   - 进入「保存恢复码」页（同 4.1）。新恢复码在发请求前就存进钥匙串 / Keystore，点「完成」才删除（服务端一换，旧恢复码就失效了，新的不能丢）。请求失败（4xx）时删除；结果不确定时保留，刷新状态后 `recovery_wrap` 等于本次上传的那份就当作成功。
4. ~~删除服务器上的明文消息~~：**0.9.0 起取消界面入口**（服务器上已经没有明文：开启加密时补加密全部历史，之后明文推送一律代加密或拒收）。以下保留作 0.8 以前的历史说明——二次确认（**T72**）后发送 `POST /v1/e2e/delete-plain {confirm: true}`，显示删除了多少条。本机已同步的明文消息保留。
   - 服务端把删掉的消息记为 `kind: "purge"` 的变更（不是 `delete`）。所有设备（包括发起删除的这台）收到 `purge` 时：本地有这条就记为「仅本机保留」，**不删除**；对账（和服务器的消息列表比对）时跳过这些 id。
   - 之后收到普通 `delete` 变更照常删除，并从「仅本机保留」里移出。
   - 变更记录只保留 90 天。离线更久的设备回来后要全量对账，这时收不到 purge：账号已开启加密时，对账发现**本地的明文消息**在服务器上找不到，记入「仅本机保留」而不删除（加密消息照常删除）。代价是离线超过 90 天期间在别的设备上删掉的明文消息，这台设备上会留着，用户可以手动删。用户在本机手动删除这类消息时只删本地，不请求服务器。不要用「删除前拍一份本地 id 快照」的做法：快照之后才同步到的明文消息会漏掉。
5. **改密码**（已升级的账号，替换原来的改密码表单）：
   - 新密码先过 `Core.passwordProblem`；
   - `salt = newSalt`，`(auth, unlock) = passwordKeys(新密码, salt)`；
   - 已开启加密时 `password_wrap = wrap("hjp1", unlock, sk)`。本机处于锁定状态时不能改，提示先解锁；
   - 发送 `PUT /v1/account/auth {current_auth_key, auth_salt, auth_key, password_wrap, kid}`（`kid` 见 §11.5，409 时显示 **T46**）。
   - 只改用户名时：`POST /v1/account/credentials {username, current_auth_key}`。
6. 状态行：「已开启 · 钥匙 <kid 前 8 位>」，以及「恢复码：已设置 / 未设置」（看 `recovery_wrap` 是否非空）。

## 8. 退出登录、设备被移除

删除本机为这个账号保存的全部私钥和设备钥匙对。「已升级」标记和钉住的账号公钥不删。

切换账号、换服务器、因读不到凭证回到登录页后登录了另一个账号时，旧账号的私钥、设备钥匙对、进行中的开启都要删除；正在进行的批准流程（请求或批准）要先停止，再删除。

服务端只在设备 token 无效或已吊销时返回 `401`（token 不会自然过期），所以 401 就等于「这台设备被移除了」。为了不被一次偶发错误误伤：收到 401 后再请求一次 `GET /v1/me`，仍是 401 才按设备被移除处理并删除私钥。

## 11. 默认自动加密（服务端 0.8.0、客户端下一版起）

目标：**所有账号都加密，没有不加密的账号**（2026-11-20 用户确认）。用户不用做任何设置，账号一有密码就自动开启端到端加密，不能关闭；用 curl 这类做不了加密的发送端，也由服务器收到后立即加密保存。§4.1 的手动「开启」页只在自动开启失败时作为出口保留。

### 11.1 自动开启

用密码的地方（注册成功、账号密码登录成功、设置初始密码成功之后），如果 `GET /v1/e2e` 的 `enabled` 为假，客户端在后台**不打扰用户**地开启：

1. 用这次刚输入的密码，按 §4.1 第 3 步计算，但：
   - 不生成恢复码，`recovery_wrap` 留空；
   - 不换密码，`auth_salt` / `auth_key` 用当前密码按 Argon2 重算（刚登录时已经算过，可以直接复用这次的 salt、auth、unlock）。
2. 「当前密码」凭证按 §2.4 计算（刚注册、刚登录时已经通过，凭证就是这次登录用的那个）。
3. 发送 `POST /v1/e2e/setup`，其余处理同 §4.1 第 4–5 步（进行中的开启照样先存进钥匙串 / Keystore，刷新时核对），区别是成功后**不弹**「保存恢复码」页，只在加密页显示提醒 **T23**。
4. `409`（别的设备刚开启过）：改为按 §4.2 用这个密码解锁。
5. 密码没通过 `Core.passwordProblem` 时**照样开启**（比明文好），同时在加密页显示 **T24**，引导去改密码。
6. 失败不影响登录：之后每次刷新（有密码凭证在内存里时）和下次用密码登录时自动重试；加密页显示「正在开启加密…」和手动开启入口（§4.1）作为出口。不提供「暂不开启」之类的选项。

配对码登录的设备没有密码，不自动开启；账号已开启时照旧是「已锁定」，用 §4.2 / §4.3 / §4.4 解锁。

**已经登录、内存里没有密码的设备**（升级到这一版之前就登录了，或者配对码登录）：账号 `enabled` 为假、服务端支持自动开启（`server_seal` 为 true；0.7 服务端没有这个字段）时，首页顶部显示提示条 **T67**，不能关闭；点开后：
- 账号有密码（`has_password`）：弹出只要求输入当前密码的小窗，按 §2.4 核对后走上面第 1–6 步；
- 账号没有密码：进入「设置密码」，设置成功后自动开启（同上）。
开启成功后提示条消失。别的设备开启后（收到 `kind: "e2e"` 变更、`enabled` 变为真），提示条也消失，本机转为「已锁定」，按 §4 解锁。

**注册即开启（0.9.0 起，2026-11-20 用户确认：注册了就是登录了，所有用户都加密）**：注册请求 `POST /v1/register` 同时带上开启加密的字段（`pub`、`password_wrap`，以及新登录协议的 `auth_salt`、`auth_key`；`recovery_wrap` 可选），服务端在同一个事务里建账号、存钥匙。账号从诞生起就是加密的，不存在「已注册但没加密」的窗口。客户端注册成功后直接按「已解锁」处理（钥匙是本机生成的，替换 / 设置钉住的公钥）。管理后台不能建账号，只能发邀请码。

### 11.2 恢复码改为可选

- 加密页「恢复码：未设置」时显示 **T23** 和「设置恢复码」按钮，流程同 §7 第 3 项（服务端接口同一个 `PUT /v1/e2e/recovery`）。
- §4.1 手动开启仍然会生成恢复码。

### 11.3 重置加密（`POST /v1/e2e/reset`）

给「忘了密码、没有别的已解锁设备、也没有恢复码」的情况，以及用户主动想换钥匙。

1. 入口：加密页「已锁定」状态下的「都不行？重置加密」，以及已解锁时的「更换加密钥匙」。二次确认 **T45**。
2. 需要当前密码（§2.4；管理员重设密码后同 §4.4 第 4 步，只有这一页允许 legacy 凭证）。
3. 计算同 §11.1（新钥匙对，不生成恢复码，不换密码），发送 `POST /v1/e2e/reset {pub, auth_salt, auth_key, password_wrap, current_…}`。
4. 服务端：旧钥匙全部标成停用（`active=0`，保留，用来让还留着旧私钥的设备继续看旧消息），删除所有 wrap（密码、恢复码、设备转交），写入新钥匙，记一条 `kind: "e2e"` 变更。
5. 成功后：保存新私钥，**用新公钥替换本机钉住的公钥**；旧私钥如果本机有，继续保留（解旧消息用）。
6. 其他设备：刷新时发现服务器 active 钥匙不是钉住的那把 → 显示 **T46**（不是 T43），引导用密码或恢复码解锁。见 §11.4。

### 11.4 钉住公钥的更新规则（修改 §4.5）

钉住的公钥只能由**服务器伪造不了**的来源更新：

- 本机生成（§4.1、§11.1、§11.3）；
- 用密码解锁拿到的私钥（§2.1 第 6 步、§4.2）：`hjp1` 用只有本机知道的 unlock_key 锁住，服务器改不了；
- 用恢复码解锁拿到的私钥（§4.4）。

这三种来源拿到的私钥，按 §4.5 第 1 条核对通过后，**替换**钉住的公钥（旧私钥保留）。设备批准（§4.3）拿到的私钥仍然必须等于钉住的公钥（核对码绑定的就是它），不能用来替换。

钉住的公钥和服务器 active 钥匙不同时，加密页显示 **T46**；只有在本机用密码或恢复码解锁后才更新，不会自动跟着服务器变。

### 11.5 服务器代加密

账号开启加密后（现在所有有密码的账号都会自动开启），用普通 pushkey 发来的明文消息，服务器收到后**立即**用账号的 active 公钥加密成同样的 `hje1` 信封再保存：

- 服务端处理顺序：校验 → 加密 → 写库 → 推送给设备；写库之后用内存里的明文转发 Bark（Bark 本来就由服务器转发明文）。数据库、备份、NAS 附件里只有密文；明文只在处理这条请求的内存里，以及上传附件的临时文件里（数据目录 `tmp/`，加密完立即删除）。
- 附件同样按 `HJF1` 分块加密，钥匙放进载荷，和发送端加密完全一样。
- 消息 JSON 多一个字段 `sealed: "server"`（发送端加密的没有这个字段）。
- 客户端解密流程不变（§6.1）。标记（2026-11-20 用户确认：接收端要告知这是明文发送）：`sealed == "server"` 时，列表里这条消息显示小标签「明文发送」（不显示 🔒），详情页元信息行显示 **T64**（不是「🔒 端到端加密」）。
- 服务器代加密**始终开启，没有开关**。加密页显示说明 **T65**（只读）。账号还没有钥匙（新建后还没有客户端登录过）期间收到的明文消息，开启后由服务器补加密（服务端是否支持见 api.md）。
- 0.9.0 起没有「只接受加密消息」：普通 pushkey 发来的消息一律由服务器代加密（简单用法，类似 PushDeer 的 curl 推送），不会以明文保存，也不会被拒收。
- 局限：`sealed` 字段由服务器给出，客户端无法验证。服务器可以把代加密的消息说成发送端加密（不带 `sealed`），所以「🔒 端到端加密」标记只表示「服务器这样声称」。要确保服务器从头到尾看不到内容，发送端必须自己用加密发送密钥。收到 `sealed` 变更时，客户端只替换「本地是明文」的记录（三端规则一致：旧记录明文、新记录 `e2e` 非空且 `sealed == "server"`、id 一致），发送端加密和已解开的消息不会被替换；但明文消息本来就没有防篡改保护，服务器可以借补加密改写本地明文副本的内容。
- **补加密的历史消息**（服务端 0.8.0）：这台设备以前同步过的明文消息，服务器补加密后：
  - 长轮询的 `changes` 里出现 `{"kind": "sealed", "id": <消息 id>}`。收到后用 `GET /v1/messages/{id}` 重新拉取这条消息：**替换**本地记录（变成 `sealed: "server"` 的加密消息），丢弃这条消息的旧附件缓存（旧附件 id 已作废），然后按 §6.1 解密显示。本机锁定时照常存成加密消息，解锁后自动解开。返回 404 时（本机设为不接收这把 key）保留本地记录不动。
  - 附件 id 换了新的：下载旧 id 返回 `410 {"reason": "sealed", "message_id": <消息 id>, …}`。**按 `reason` 判断**（不要比较错误文字）：`sealed` → 用 `GET /v1/messages/{message_id}` 重新拉取这条消息（同上），**不要**记成「附件已丢失」，也不要把半截下载的文件和新文件拼起来（续传要重新开始）；`missing`（或没有 `reason` 的旧服务端）才是附件文件丢失。离线超过 90 天的设备收不到 `sealed` 变更，只能靠这个 410 发现，所以两条路径都要实现。
- **上传锁住的私钥副本时带 kid**（服务端 0.8.0）：改密码（`PUT /v1/account/auth` 的 `password_wrap`）、换恢复码（`PUT /v1/e2e/recovery`）、批准设备（`POST /v1/e2e/grant`）时，一并发送 `kid` = 本机私钥对应公钥的 kid（`Core` 里和信封同一个算法）。服务器发现它不是账号启用中的钥匙时返回 `409`：说明账号在别的设备上重置过加密，本机拿的是旧私钥，显示 **T46**，引导用密码或恢复码解锁新钥匙后再操作。

### 11.6 发送端默认用加密发送密钥

- Pushkey 页：每把 key 默认复制的是加密发送密钥（§7 第 1 项，规则不变）；普通 key 收进「显示普通 pushkey」折叠项，说明 **T66**。
- 新建 key 后弹出的结果页同样优先显示加密发送密钥。
- 管理后台 Pushkey 页同时显示两种（管理后台本来就是服务器，用数据库里的公钥）。

## 12. 配对码带钥匙（服务端 0.10.0、功能 id `pair.key`）

目标：用配对码登录的新设备**直接解锁**，不用再输密码、等批准或输恢复码。已解锁的设备生成配对码时，顺便把账号私钥用一把一次性钥匙锁住交给服务器暂存；这把一次性钥匙只出现在二维码和长配对码里，从不经过服务器。

### 12.1 格式

- 一次性钥匙 `S`：16 字节随机数（128 位），显示成和恢复码一样的 26 位 Crockford base32（`XXXXX-XXXXX-XXXXX-XXXXX-XXXXXX`）。
- 锁住的私钥 `key_wrap` = `wrap("hjc1", K, 账号私钥)`，`K = HKDF-SHA256(salt="huijian pair v1", ikm=S)`；AES-256-GCM，附加数据是前缀 `hjc1`（和 `hjp1`、`hjr1` 同一种格式）。
- **长配对码**：6 位配对码 + 一次性钥匙，`123456-XXXXX-XXXXX-XXXXX-XXXXX-XXXXXX`。
- **配对链接**（二维码的内容）：`huijian://pair?server=<URL 编码的服务器地址>&code=<长配对码>`。

共用核心的操作（各端不要自己拼）：

| 操作 | 参数 → 结果 |
|---|---|
| `pair_key_new` | `{sk}` → `{secret, wrap}`：生成 S 并锁住私钥 |
| `pair_key_open` | `{secret, wrap}` → `{data}`（私钥）；钥匙不对报 `format` |
| `pair_format` | `{server, code, secret}` → `{text, link}`：长配对码和配对链接 |
| `pair_parse` | `{input}` → `{code, secret?, server?}`：接受 6 位配对码、长配对码、配对链接（容忍空格、小写、`O`/`I`/`L`），格式不对报 `format` |
| `qr` | `{text}` → `{size, modules}`：二维码矩阵，`modules` 是 `size × size` 个 `0` / `1`（按行），不含四周留白（显示时四周各留 4 格） |

### 12.2 生成（已登录的设备，「添加设备到这个账号」）

1. 本机已解锁（有账号 active 钥匙的私钥），并且服务端有功能 `pair.key`：
   - `(secret, wrap) = Core.pairKeyNew(sk)`；
   - `POST /v1/pair-codes {key_wrap: wrap}`；
   - 用返回的 `code` 和 `secret` 算出长配对码和链接，显示**二维码**、**长配对码**（可复制）、倒计时，文案 **T80**。
2. 本机没解锁或服务端没有 `pair.key`：和原来一样只发 `POST /v1/pair-codes`、只显示 6 位配对码，并显示 **T81**。
3. `secret` 只放在内存里：重新生成、离开页面、过期、被使用后都清掉，不写日志、不落盘。
4. 被使用后（`state: used`）照旧显示是哪台设备。

### 12.3 使用（新设备）

1. 登录页「配对码」输入框接受 6 位配对码、长配对码、配对链接，统一用 `Core.pairParse` 解析：
   - 链接里带服务器地址时填进服务器地址栏（用户能看到，可以改）；
   - iPhone、安卓在输入框旁边有「扫码」按钮，用相机扫描二维码；Mac 可以粘贴链接或长配对码（从 iPhone 复制后用通用剪贴板粘贴）。
   - 系统打开 `huijian://pair?…` 链接时（例如用系统相机扫码）：没登录 → 打开登录页并填好；已登录 → 提示 **T84**，不做任何事。
2. `POST /v1/pair {code: 6 位配对码, …}`（`S` **不**发给服务器）。登录成功后看响应里的 `key_wrap`：
   - 输入里有 `S`、响应有 `key_wrap`：`Core.pairKeyOpen(S, key_wrap)` 得到私钥；解不开时显示 **T82**，登录照常成功，进入「已锁定」状态。
   - 输入里有 `S`、响应没有 `key_wrap`（服务端太旧，或生成它的设备没解锁）：进入「已锁定」，显示 **T83**。
   - 输入里没有 `S`（只输了 6 位）：和原来一样进入「已锁定」。
3. 拿到私钥后，和密码登录一样等取到账号 id（`/v1/me`），再按 **§4.5 第 1 条**核对（必须是 `GET /v1/e2e` 里一把 active 钥匙）后保存。
4. 它算作 **§11.4 的可信来源**（和密码、恢复码同级）：`hjc1` 用只出现在你两台设备之间的 S 锁住，服务器伪造不了，所以核对通过后可以替换本机钉住的公钥。
5. `S` 用完即弃，不落盘。

### 12.4 服务端

- `pair_codes` 加一列 `key_wrap`。`POST /v1/pair-codes` 可以带 `{key_wrap}`：必须以 `hjc1.` 开头、不超过 256 字节，否则 400。
- `POST /v1/pair` 成功时，有 `key_wrap` 就在响应里返回，并立即从数据库清空；没用掉的配对码过期后也清空。
- 重置加密（`POST /v1/e2e/reset`）时，作废本账号所有带钥匙、还没用掉的配对码（里面锁的是旧钥匙）。
- 服务器只暂存密文，拿不到 S，解不开；配对码本身（6 位）的限速、3 分钟有效、只能用一次不变。

### 12.5 安全说明

- 谁拿到长配对码（或二维码照片），3 分钟内就能登录这个账号**并且看到加密消息**。所以 T80 提醒只给自己的设备用；6 位配对码被猜中只能登录、看不到内容，和以前一样。
- 服务器既拿不到 S，也没法把锁住的私钥换成别的：AES-GCM 改一个字节就解不开。服务器把新设备登进别的账号时，解出来的私钥和那个账号的 active 钥匙对不上，§4.5 会拒绝。
