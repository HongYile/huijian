# 端到端加密设计（草案）

> 状态：已确认，实施中。先在自建版（rock）上线，稳定后用于官方服务。

## 目标

- 消息的标题、正文、附件（含文件名）只有你自己的设备能解开。服务器、服务器管理员、云厂商、备份文件里都只有密文。
- 发送端（脚本、agent、训练任务）**只能加密、不能解密**：发送配置泄露了，别人最多能冒充你发消息，看不到任何历史。
- 性能开销小：每条消息只多一次密钥协商（微秒级），附件加解密用硬件加速的 AES，手机上也接近磁盘速度。
- 用标准、经过广泛审查的算法和构造，不自己发明密码学。

## 算法选择

| 用途 | 选择 | 理由 |
|---|---|---|
| 消息加密 | **HPKE**（RFC 9180，base 模式）：DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + **AES-256-GCM** | IETF 标准的「用公钥加密」构造，TLS 1.3 / MLS 同一系列；每条消息用一次性密钥，互不影响 |
| 附件加密 | AES-256-GCM 分块（每块 64 KB，块序号参与 nonce 和附加数据，最后一块带结束标记） | 大文件可以边下边解、断点续传；块不能被删、换序、截断 |
| 密码派生 | **Argon2id**（RFC 9106，64 MiB、3 轮） | 密码哈希竞赛冠军、OWASP 首选；占内存，显卡和专用芯片难以批量暴力破解 |
| 设备之间转交钥匙 | 同样用 HPKE，加密给新设备的临时公钥 | 只有那台新设备解得开 |
| 恢复码 | 128 位随机数（26 位字母数字，分 5 组显示），HKDF 派生加密密钥 | 熵足够高，不需要慢哈希也不可能暴力破解，解锁瞬间完成 |
| 设备上保存私钥 | Apple 钥匙串（仅本机，不同步 iCloud）/ 安卓 Keystore 包裹 / Windows DPAPI | 系统级保护，App 卸载即清除 |

为什么选 AES-256-GCM 而不是 ChaCha20：Mac、iPhone、安卓（8.0 起）、Windows 的 CPU 都有 AES 硬件指令，系统库原生支持，最快也最省电。

各平台都用系统或主流实现，不用小众库：Apple CryptoKit（HPKE、AES-GCM 原生）、Go 标准库（crypto/ecdh、crypto/hkdf、crypto/aes）、安卓（AES-GCM 用系统 javax.crypto；X25519 在安卓 12 以下系统没有，用 Google Tink）、Windows 版 Rust 用 RustCrypto 的 hpke / aes-gcm。各端用 RFC 9180 的官方测试向量互相验证。

**抗量子**：格式里带版本号。等各平台都原生支持 X-Wing（ML-KEM-768 + X25519 混合）后升级，旧消息照常能解。推送内容时效性短，现在不急。

## 钥匙

每个账号一对**加密钥匙**（X25519）：

- **公钥**：公开的，发送端用它加密。
- **私钥**：只在你登录了的设备上；服务器上只存「锁住的副本」，自己解不开：
  - 用密码派生的解锁钥匙锁住的一份（AES-256-GCM），日常登录就靠它；
  - 加密给经批准的设备的副本（HPKE，忘记密码时用）；
  - 用恢复码锁住的一份（强烈建议保留）。

### 新设备怎么拿到钥匙

**日常：账号密码登录就自动解锁**（Bitwarden、1Password 的做法）。
- 新设备输入账号密码后，**在本机**用 Argon2id 从密码派生出 64 字节：前 32 字节是**登录凭证**，发给服务器验证身份；后 32 字节是**解锁钥匙**，永远不离开设备，用来解开服务器上存的「用密码锁住的私钥」。
- 服务器只拿得到登录凭证（它也只存凭证的哈希），推不出解锁钥匙，也就解不开私钥。
- Argon2id 参数：64 MiB 内存、3 轮、单线程，盐由服务器为每个账号随机生成。手机上约 0.3–0.5 秒，只在登录、改密码时算一次。
- 开启加密时要求密码至少 10 位，并拒绝常见弱密码：服务器数据被偷时，弱密码仍可能被离线猜中。服务器拿不到密码，这项检查由客户端做。
- **邮箱验证码**作为登录的第二道关（防止别人拿到密码直接登录），不参与加密。官方服务默认开启；自建版配置了邮件服务（SMTP）就能开。
- 改密码：在已登录的设备上用新密码重新锁一份私钥上传，旧的那份作废。

**备用：忘记密码时**
1. **另一台已登录设备批准**：两台设备显示同一个 6 位核对码，核对一致后点批准，私钥用 HPKE 加密转交给新设备，然后重新设置密码。
   - 核对码用「先承诺、后揭晓」算出（ZRTP、Signal 的做法）：新设备先交出随机数的哈希，批准设备再给出自己的随机数，新设备最后揭晓。服务器想冒充新设备，必须在看到批准设备的随机数之前就定下自己的，没法反复试出相同的核对码，每次冒充只有百万分之一的机会，失败还会被用户看到。
   - 只用公钥哈希算 6 位码是不够的：被攻破的服务器几秒内就能生成大量密钥对，挑出核对码相同的一个。
   - 承诺和核对码里还包含新设备看到的**账号公钥**，批准设备用自己私钥算出的公钥核对；新设备只接受和这把公钥配对的私钥。否则服务器可以给新设备看自己的公钥、再伪造一份转交（HPKE 转交谁都能加密给新设备），让新设备收下服务器的私钥。
2. **恢复码**：所有设备都丢了、又忘了密码时，用开启加密时显示的恢复码解锁。恢复码只显示一次，请抄下来或存进密码管理器。

**登录协议的变化**：新版客户端从不把密码原文发给服务器。登录前先取这个账号的派生参数和盐，再发送派生结果。旧账号第一次用新版客户端登录时，发送的是按服务器原有密码哈希的盐算出的 PBKDF2 结果（同样不是原文），登录后自动升级到 Argon2id。

客户端把 Argon2id 参数写死，并记住账号已经升级过：即使服务器被攻破，也没法用弱参数或谎称「这是旧账号」骗出能快速破解的派生值。

开启加密时，客户端建议换一个新密码（默认勾选）。原因是旧密码以前以原文形式发给过服务器，旧备份里还有它的 PBKDF2 哈希。配对码登录的设备没有输入密码，用「另一台设备批准」或输入一次密码解锁。

### 发送端怎么拿到公钥

客户端的 Pushkey 页提供一个**加密发送密钥**：`PK_xxx.e2e.<公钥>`（公钥 43 个字符）。
- 发送端用它加密；服务器把 `.e2e.` 之前的部分当作 pushkey 识别。
- 公钥直接写在密钥里，而不是向服务器要：服务器即使被攻破，也没法偷换成自己的公钥来截获消息。
- 客户端显示的加密发送密钥同样不用服务器给的公钥：每台设备第一次拿到账号私钥时，记下（钉住）它算出的公钥，以后只显示这把。
- 旧格式的 pushkey 照常可用，发出的是明文消息。

### 钥匙泄露和更换

- **重置加密**（服务端 0.8.0，`POST /v1/e2e/reset`）：忘了密码、又没有恢复码和其他已解锁的设备时，或者想主动换钥匙时，用当前密码换一把新钥匙。旧钥匙全部停用但保留在服务器上（还留着旧私钥的设备照样能看旧消息），所有锁住的副本（密码、恢复码、转交给设备的）一律删除，进行中的设备批准作废。其他设备发现账号的钥匙不是自己钉住的那把时，要用密码或恢复码重新解锁，才更新钉住的公钥（设备批准拿到的私钥不能用来替换，见 e2ee-client.md §11.4）。
- （以后的版本）移除了丢失的设备后，可以选择「更换加密钥匙」：生成新钥匙，转交给剩下的设备，旧消息仍然能看（旧私钥也一起转交）。服务端已经按「有效 / 已停用」区分钥匙：停用的钥匙不再接收新消息。
- 更换后发送端要换成新的加密发送密钥（客户端里一键复制）。
- 实现更换时要同时更新各设备钉住的账号公钥（只能由转交来的新私钥算出，不能听服务器的）。

### 加密保证什么、不保证什么

- 保证**保密**：服务器、数据库、备份里只有密文。
- 已知局限：
  - Mac 版没有开发者签名时用不了「数据保护钥匙串」，私钥存在 login 钥匙串里：不会同步到 iCloud，但迁移助理和整机备份会把它带到别的 Mac。
  - 管理员重设密码后的「重新设置密码」页要用旧方式核对当前密码。被攻破的服务器可以谎称「管理员重设过」，用户如果在这一页填了自己真正的密码，服务器能拿到它的 PBKDF2 结果（比 Argon2 好猜）。页面会提示只填管理员给的临时密码。
- 不保证**来源**：拿到加密发送密钥的人、以及服务器本身都能往账号里塞一条加密消息，也能改优先级、频道，或重放旧消息。客户端显示 🔒 只表示「内容加密了」，不表示「一定是你的脚本发的」。

## 服务器代加密（0.8.0）

0.8.0 起账号一有密码就由客户端自动开启加密（恢复码改为可选）。curl 这类做不了加密的发送端，用普通 pushkey 发来的明文消息由服务器**收到后立即**用账号的公钥加密再保存。所有账号都加密，代加密始终开启，没有开关。

- 格式和发送端加密完全一样（同样的 `hje1` 信封、载荷和 `HJF1` 附件），客户端解密流程不变；消息多一个 `sealed: "server"`，客户端显示「🔐 服务器加密」，不显示成端到端加密。
- **比端到端加密弱**：服务器在收到请求的那一刻能看到标题、正文和附件。被攻破的服务器（或者能看到服务器内存、能改服务器程序的人）可以在这一刻记下内容；转发 Bark 时也照旧用明文（Bark 本来就由服务器转发明文）。想让服务器完全看不到，要用加密发送密钥在发送端加密。
- **保证的是落盘的数据**：数据库、备份、附件目录（包括放在 NAS 上的）里只有密文。明文只存在于处理这次请求的内存里，上传的附件先写到临时文件，加密完立即删除（失败也删）；附件目录名用占位标题，不出现真实标题。数据库被拷走、备份被偷、NAS 被别人看到，都拿不到内容。
- 服务器自己生成的消息（管理后台的测试消息、存储告警等系统通知）同样加密。
- 「只接受加密消息」打开时明文直接拒收，不走代加密：用来确认所有发送端都已经在本机加密。
- **补加密**：账号还没有钥匙期间（以及开启加密以前的历史）存下的明文消息，开启后由服务器在后台补加密，服务启动时也会再补一遍；附件读不到的先跳过、下次再试，剩下的可以用「删除服务器上的旧明文消息」清理。补加密改的是服务器上的副本：已同步到设备上的本地副本不变，之前的备份（数据库快照、只增不删的附件镜像）里仍有明文，需要时手动删除旧备份。
- 补加密之后，这些历史消息也只有拿到账号私钥的设备能看：如果忘了密码、又没有恢复码和其他已解锁的设备，只能重置加密，旧消息就再也看不到了。

## 加密什么、不加密什么

| 内容 | 是否加密 | 说明 |
|---|---|---|
| 标题、正文（Markdown 原文） | 加密 | |
| 附件内容、文件名、类型 | 加密 | 服务器只看到大小和一个随机 id |
| 优先级 | **不加密** | 服务器要按优先级决定提醒方式、转发 Bark |
| 频道（topic）、线程（thread） | **不加密** | 频道改名、静音、隐藏这些功能需要；频道名请避免写敏感信息 |
| 发送时间、来源 pushkey | 不加密 | |

## 对现有功能的影响

| 功能 | 加密后 |
|---|---|
| Markdown 渲染 | 改为**客户端解析**（服务器看不到原文）。各端用成熟的 CommonMark + GFM 库，加上回笺扩展（提示框、进度条、正文附件、单换行即换行），用同一套测试样例保证各端显示一致：Mac / iPhone 共用一份 Swift 实现，安卓用 commonmark-java，Windows 用 Rust 的 comrak |
| 锁屏通知（Mac、安卓、iPhone 打开时） | 在本机解密后显示完整内容，和现在一样 |
| iPhone 锁屏（经 Bark） | 服务器读不到内容，见下文「待确认」 |
| 管理后台 | 只显示「🔒 加密消息」、频道、优先级、大小，看不到内容 |
| 附件去重 | 同一个文件发两次会存两份（每次加密结果都不同） |
| 搜索 | 只在客户端本地搜 |
| 发送 | 回笺 skill、`huijian` 命令行、Python SDK 自动加密；直接 curl 只能发明文，0.8.0 起由服务器收到后代为加密（标「🔐 服务器加密」） |
| 旧消息 | 0.8.0 起开启加密后由服务器补加密（见上文「服务器代加密」）；补不了的（附件读不到）可以用「删除服务器上的旧明文消息」删掉，本机已同步的保留 |

可选的账号设置「**只接受加密消息**」：打开后服务器拒收明文消息，防止有脚本忘了换成加密密钥。

## 发送端

- `huijian push`（Go 命令行）和服务端同一套代码，内置加密。
- Python SDK：装了 `cryptography` 库就自动加密（绝大多数环境已经有）；没有时提示安装，或者明确选择发明文。
- 回笺 skill 改成优先用命令行或 Python SDK 发送；只有 curl 时提醒用户内容是明文。

## 实施步骤

1. 加密格式和测试向量（Go），服务端：存公钥、锁住的私钥副本、设备批准流程、加密消息和附件的存储与转发、「只接受加密消息」开关。**已完成（服务端 0.7.0）**，接口见 [api.md](api.md)「端到端加密」。
2. 客户端 Markdown 本地解析（Swift、Kotlin），用服务端现有测试样例对齐。
3. 三个客户端：开启加密、恢复码、设备批准、解密显示、加密附件下载、「未加密」标记。
4. 发送端：命令行、Python SDK、回笺 skill。
5. rock 上自己先用；之后 Windows 版直接按加密版开发。
